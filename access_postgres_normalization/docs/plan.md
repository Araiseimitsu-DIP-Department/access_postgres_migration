# PostgreSQL 正規化の計画と作業手順

## 目的と初期状態

Accessから移行した複数DBに保存されている同じ情報を整理し、項目ごとの管理元とアプリの読み書き先を明確にする。業務上必要な帳票の確定値・履歴・業務固有属性は、保存時点と用途を確認して設計する。

2026-11-19 のアプリ調査（[NASアプリとDBの対応](app-db-inventory.md)）で、現品票履歴の2テーブルはアプリの実行コードから参照されていないことが分かった。そのため、11アプリが参照する `delivery_label_db.delivery_label_history` と、4DBに分かれた `product_master` を優先度1とし、下表の現品票履歴は後順位とする。

事前調査では、本番と開発の27 DBでテーブル・列・制約の定義が一致した。主要27テーブルのデータは18テーブルが一致し、9テーブルに差があった。以下の件数は事前調査時点の観測値とし、実装前に開発環境で再計測する。

| 順序 | 対象 | 事前調査の結果と着手条件 |
|---|---|---|
| 1 | 現品票履歴 | 外観検査の33,987件が現品票の35,817件に全11列一致で含まれていた。まず両方の書き込み元と、現品票側だけにある1,830件の閲覧要件を調べる。 |
| 2 | 製品・機械・仕入先 | 受注管理の1,586品番と委託加工の1,573品番が共通製品マスタと品番・客先で一致。受注側では単価28件、締日26件に差があった。材料手配の機械59件と仕入先13組も共通候補と一致。項目別の管理元を確定してから参照を切り替える。 |
| 3 | 製品工程・外観検査・二次工程 | 製品マスタの工程②〜⑨、検査者1〜5、不具合種別の列を明細化する候補。欠番、入力順、未入力と0件、工程固有の入力を維持できる設計を先に決める。 |
| 4 | 受注・納品・出荷検査・委託加工 | 受注管理と受注実績は注文IDが39,358件共通で、比較対象の13項目すべてが一致したのは38,667件。委託加工では発注先の行が見つからない納入が3,295件。明細の単位、未一致の由来、帳票の履歴要件を先に確認する。 |
| 5 | 材料入庫・作業用データ・バックアップ | 材料入庫の単位や検査の `purchase_id` の参照先を調査する。生産リリースのバックアップは30,193件中、全列一致が7,334件。差分の保存目的を確認して整理方針を決める。 |

## 手順1　開発環境で再計測する

1. 接続先を開発環境と確認し、読み取り専用で対象DBとテーブルの定義を採取する。調査結果は測定日時、接続先、比較した列、件数をセットで記録する。
2. 現品票履歴の監査を [README](../README.md) のコマンドで実行する。一致は全11項目の値を比較し、NULLと同一行の出現回数も照合する。
3. 次の対象ごとに、候補キーのNULL・空欄・重複、片側にしか存在しないキー、同じキーで値が異なる項目を集計する。品番などの照合は元の値を保存した上で、前後空白を除く等の比較ルールを明記する。
4. 開発環境を再同期するときは、同期点を記録して再計測する。正規化の検証結果は、その時点のデータと対応付ける。

## 手順2　アプリと保存目的を確認する

1. 関係アプリの接続設定、ORM、SQL、取込ジョブ、帳票を検索し、実際の読み書き先を画面・API・バッチ単位で洗い出す。
2. 現品票ではロット検索、一覧、登録、訂正、再取込を確認する。両履歴の書き込み経路、外観検査が表示する行の範囲、同じロットの複数行が何を表すかを確認する。
3. 各マスタで誰が更新するかを項目ごとに確認する。製品では品番と客先の照合結果に加え、単価と締日が現在値・取引時点の値・業務固有の値のどれかを調べる。
4. 未確認項目は [アプリ接続先の対応表](app-mapping.md) に残す。必須の読み書き先と期待結果が確定してから、切替対象に含める。

## 手順3　新しい表と移行SQLを設計する

1. 現品票は `delivery_label_db.public.excel_delivery_label_history` を共通の管理元候補とする。登録・訂正の経路が確認できたら、共通の履歴表を新設するか、既存表を共通参照先にするかを決める。
2. 互換性の検証では、現品票側だけにある行を外観検査が閲覧してよいかを先に決める。従来の範囲が必要なら、対象行を識別できる対応表や参照条件を設計する。ロットID単独の一意性は実データで確認する。
3. 製品マスタは共通IDと旧DB側の識別子の対応を保存する。未一致・複数一致の候補を一覧化し、解決済みの対応だけで移行する。必要に応じて業務固有の属性を共通IDにひも付ける。
4. PostgreSQLの外部キーをDB横断で設定することはできない。DBを維持する案では、アプリ側の複数接続や取得処理の共通化を検討する。DB側で参照整合性を保証する要件がある場合は、対象を同一DB内の業務別スキーマに配置する案を検討する。
5. 対象ごとに、事前確認・追加DDL・投入・検証を分ける。元テーブルのキーを移行先へ対応付け、再実行で行が増えず、失敗後に再開できる処理にする。同一DB内ではトランザクション単位を明記し、別DBへの処理は工程ごとにコミットと再開条件を決める。

## 手順4　開発環境で検証する

1. 既存テーブルを使用したまま、新しい表や参照先を作成してデータを投入する。接続先と対象テーブルを実行前に出力する。
2. 旧側の対象件数が、移行済み・保留などの内訳と一致することを確認する。旧画面相当の検索条件で、行数、列値、NULL、並び順、複数行の扱いを比較する。
3. 再度実行し、件数が不必要に増えないことを確認する。検証環境で途中失敗を再現し、再実行で整合することを確認する。
4. 対応表に沿って検索・登録・訂正・再取込・帳票をテストする。現品票は片側にしかない行、製品は価格や締日の差分、委託加工は発注先の行が見つからない納入を検証に含める。
5. 読み取りを切り替えた後に旧経路へ戻す手順を確認する。書き込みも切り替える場合は、新経路で受け付けた更新の退避・旧側への反映と再検証まで試す。

## 手順5　本番切替を判断する

1. 開発での検証結果、アプリ変更、業務ごとの責任者、予定する停止時間、切替・切戻しの担当を確認する。
2. 本番の最新状態で監査を再実行する。初回投入後の更新は、確定した更新キーで反映するか、書き込みを止めた時間帯に再照合して取り込む。差分を取り込めない状態では切替を延期する。
3. アプリ単位でまず読み取り先を切り替え、件数・値・エラーを確認する。書き込み先の切り替え時には対象画面を特定し、旧・新の双方で同じ取引を登録しない手順を決める。
4. 表示差分、更新エラー、未解決の参照欠落が検出された場合は切り戻す。書き込み切替後は、更新を一時停止し、切替後に新側で受けた変更を確認・反映してから旧経路に戻す。
5. 旧テーブルの削除・初期化などが必要になった場合は、対象環境・テーブル・影響するアプリ・復旧方法を提示して事前承認を得る。

## 後続の段階で扱う課題

製品マスタの一本化（2026-11-19、開発DB）で残した設計上の課題。全アプリに影響するため、対象ごとの切替が落ち着いてから別段階で計画する。

| 課題 | 現状のリスク | 方針 |
|---|---|---|
| アプリ別のDBロール | 全アプリが `postgres` で接続し、設定誤りがあると任意のDBを変更できる | アプリごとに必要なDB・表だけの権限を持つロールを作り、接続設定を切り替える |
| DBの統合 | DBをまたぐ外部キーを設定できず、外部テーブル経由の参照は参照先DBの停止に影響される | 業務別スキーマを持つ単一DBへの統合を検討し、製品は `id` での参照に寄せる |
| 管理表Excel運用の廃止 | 品番の登録経路が管理表と受注管理画面の2つあり、IDの採番が分かれる | 正規化が安定した後、製品登録を画面に一本化し、Excel取込を停止する |

## 実装の開始条件

現品票の読み取り専用監査は実行可能。正規化用DDLと移行SQLは、対象アプリの書き込み経路と外観検査の表示範囲を確認した後に実装する。対象ごとに、出力するスクリプト、対応表、検証結果、切り戻し手順が揃った時点を開発完了とする。
